# Granola-like 功能架构评估

## 总结结论

**适合在当前项目上继续实现个人日常使用的 Granola-like MVP，但不适合直接在现有入口上堆功能。** 当前仓库已经具备本地语音助手所需的若干底层能力：使用 `sounddevice` 采集默认音频输入，使用 Whisper 或 llama-server 的 OpenAI 兼容 ASR 转文字，使用 Ollama/llama-server 调用 LLM，并使用进程内会话历史组织对话。上述能力可以复用。

但是，用户要求的核心能力目前都没有完整实现：没有“会议”数据模型和无限会议列表，没有持续会议录音和可靠分段，没有系统播放设备或会议应用音频的 loopback 捕获，没有会议转写结果持久化，没有专门的纪要生成流程，也没有本地数据库、任务恢复、检索或导出能力。因此当前代码是**可复用的音频/AI原型底座**，不是可直接增强为产品的会议应用。

建议先做 Windows 优先的桌面 MVP：用户明确点击开始/停止，在本机选择麦克风或 WASAPI loopback 设备，原始音频按块写入磁盘，停止后离线转写，再按文本块调用 LLM 生成结构化纪要，并将会议、转写和纪要保存到 SQLite。这个方案不需要机器人加入会议，也不依赖会议平台 API。macOS 的系统音频采集放到后续阶段，因为通常需要虚拟音频设备或系统级音频捕获方案，且权限和设备路由更复杂。

“会议数量不限”在产品层面可以实现为不限制用户创建数量；在工程层面仍受磁盘、模型处理时间、数据库大小和备份能力限制，不能承诺物理意义上的无限容量。

## 证据和当前已有能力

以下判断来自静态阅读，引用均为仓库中的文件和函数/符号。没有启动模型服务、打开录音设备或执行端到端会议录音，因此凡是依赖本机硬件、模型、权限或服务的能力都标记为“需要运行时验证”。

### 音频输入和录音

- `app_win.py:record_audio()` 和 `app_mac.py:record_audio()` 使用 `sounddevice.RawInputStream`，固定为 16 kHz、单声道、16-bit，并通过回调把音频字节放入 `Queue`。这证明项目已有**默认输入设备的麦克风采集路径**。
- 两个入口都调用 `sd.query_devices()`，筛选 `max_input_channels > 0` 的设备；没有默认输入设备时才让用户选择设备。这是一个可复用的设备枚举基础，但不是持久化的设备选择配置。
- Windows 入口已有 `record_until_silence()`、`continuous_listen_for_wake_word()` 和 `listen_in_wake_mode()`，可复用其中的线程控制和音频块拼接逻辑，但它们面向短问答，不适合直接作为长会议录音器。
- 现有录音只接入默认输入设备。代码没有配置 WASAPI loopback、立体声混音、虚拟音频线、应用级捕获或麦克风与扬声器混音，因此**不能从静态代码确认能够采集 Zoom、Teams、浏览器等会议的系统播放音频**。当前可确认的是“本机麦克风输入”，而不是“设备上所有会议音频”。系统音频采集需要新增能力并进行运行时验证。
- `record_until_silence()` 用“队列是否收到数据”判断是否静音，而 `RawInputStream` 在环境噪声中仍持续产生数据；这不是可靠 VAD。长会议不应依赖该停止条件。
- `Queue` 没有容量上限，也没有落盘写入线程、丢块统计、磁盘空间检查或录音恢复机制。长时间录音时存在内存增长和进程退出丢失全部音频的风险。

### ASR/转写

- `stt.py:numpy_to_wav_bytes()` 能把 NumPy 音频编码为 16 kHz、单声道、16-bit WAV，可复用为转写输入格式化函数。
- `stt.py:transcribe_whisper()` 调用已加载的 Whisper 模型；`app_mac.py` 默认加载 Whisper `base`，`app_win.py` 默认加载 `small`。这提供本地 ASR 能力，但当前调用是“整段音频转写”，没有长音频切块、时间戳、重试、增量转写或说话人识别。
- `stt.py:transcribe_llama_asr()` 调用 `{base_url}/audio/transcriptions`，发送 WAV 和模型名，并使用默认 600 秒超时。它可复用为可选远程/本地服务适配器，但转写依赖 llama-server 运行且会把音频发送到该服务；隐私边界需要明确。
- `stt-test.py` 只是人工冒烟脚本，固定读取 `sample-zh.wav` 并访问 `localhost:8080`，不是自动化测试。ASR 服务是否可用、指定模型是否实际可加载，需要运行时验证。
- 当前代码没有保存转写文本、时间戳、分段状态或原始音频元数据。因此“自动生成会议纪要”的输入管线尚未存在。

### LLM

- `app_mac.py` 用 `langchain_ollama.OllamaLLM`，默认访问 `http://localhost:11434`，默认模型是 `gemma3:1b`。
- `app_win.py` 用 `langchain_openai.ChatOpenAI`，默认访问 `http://localhost:8080/v1`，默认模型来自 `LLAMA_SERVER_MODEL`。`query_local_llm.py` 和 `actor-critic-sample.py` 也证明仓库已有 OpenAI 兼容调用方式。
- 两个主入口都用 `ChatPromptTemplate`、`RunnableWithMessageHistory` 和 `InMemoryChatMessageHistory`。这可复用为纪要生成的 LLM 调用层参考，但当前 system prompt 是对话助手提示词，不是会议总结提示词；`app_mac.py` 还明确要求回答少于 20 个单词，不能直接产生完整会议纪要。
- `chat_sessions` 是进程内字典，固定使用 `voice_assistant_session`。它不是会议存储：进程重启后丢失，不支持会议列表、按会议查询、跨会议检索或多人/多会议隔离。
- `actor-critic-sample.py` 有独立的 Actor-Critic 文本修订示例，但没有接入录音或会议数据，也不能替代结构化纪要流水线。它最多可作为未来的纪要质量复核实验参考。
- LLM 能否按指定模型成功响应、上下文长度是否足够、长转写是否需要分块和汇总，目前都需要运行时验证。

### TTS 和输出

TTS 不是用户目标的必需能力，但项目已有它：`tts.py:TextToSpeechService` 使用 Chatterbox，可选择 CUDA、MPS 或 CPU；`app_win.py` 中文分支使用 `pyttsx3`，非中文分支使用 Chatterbox。会议纪要 MVP 不应优先复用 TTS，因为它会增加模型加载、GPU/CPU 占用和平台依赖；可在后续提供“朗读纪要”时复用。

### 配置和依赖

- `app_mac.py` 和 `app_win.py` 使用 `load_dotenv()`。当前可确认的环境变量包括 `OLLAMA_LLM_BASE_URL`、`OLLAMA_LLM_MODEL`、`LLAMA_SERVER_MODEL`、`LLAMA_SERVER_BASE_URL`、`STT_BACKEND`、`LLAMA_ASR_BASE_URL` 和 `LLAMA_ASR_MODEL`；报告不复述 `.env` 的具体值。
- `pyproject.toml` 要求 Python `>=3.11`，声明 `sounddevice`、`openai-whisper`、`langchain`、`langchain-ollama`、`pyttsx3`、`chatterbox-tts`、`torchaudio` 等依赖；`requirements.txt` 还包含 `soundfile`、`requests`、`langchain-openai` 和 Windows 相关包。两份依赖清单并非完全一致，新增会议功能前需要统一安装入口。
- `README.md` 的安装说明要求下载 NLTK 数据并启动 Ollama，但它仍包含不存在的 `app.py` 示例，且没有会议功能说明。文档不能作为当前会议能力的证明。
- `.gitignore` 忽略 `.env`、`*.wav`、数据库常见路径 `db.sqlite3` 和模型/缓存目录；新增持久化文件时必须选择明确的数据目录，并确认不会误提交个人录音和转写。

### 持久化和测试

静态搜索未发现 SQLite/SQLAlchemy 数据模型、JSON/YAML 持久化、会议/转写/纪要实体或索引实现。除可选地把 TTS 输出保存到 `voices/` 外，主流程不保存用户会话、录音或转写。仓库也没有项目自己的 `pytest`/`unittest` 测试文件或测试配置；现有 `stt-test.py` 需要外部服务，不能作为回归测试。此结论可由代码静态确认，不需要运行时验证。

## 需要新增的能力

要满足“个人日常使用、会议数量不限、自动纪要、不进机器人、采集本机设备音频”，至少需要新增以下模块或职责：

1. **会议生命周期**：会议 ID、标题、开始/结束时间、状态、设备配置、错误状态和删除/归档操作。
2. **可靠录音器**：设备枚举与显式选择，麦克风模式和系统 loopback 模式，持续写 WAV/FLAC 分块，录音线程与写盘线程解耦，停止/异常时安全关闭文件，并记录采样率、声道、设备名。
3. **Windows 音频捕获**：优先验证 WASAPI loopback 能否捕获默认播放设备；必要时提供麦克风、loopback 或混合输入选项。不能假设 `sounddevice.RawInputStream` 的普通默认输入就是系统播放音频。
4. **macOS 音频捕获**：需要验证可用的系统音频路由或虚拟设备，并处理麦克风/系统录音权限；不要把 Windows 的方案直接移植到 macOS。
5. **转写流水线**：按时长或文件大小切块，异步排队，保留每块状态和重试次数，记录文本、起止时间、语言和 ASR 后端；首版可以不做实时转写，停止会议后批处理更可靠。
6. **纪要生成器**：把转写分块合并或先做层级摘要，要求 LLM 输出固定结构，例如摘要、决策、行动项、负责人、截止时间、风险和待确认问题；必须保留原始转写，防止纪要错误覆盖证据。
7. **持久化**：优先 SQLite，至少设计 `meetings`、`audio_chunks`、`transcript_segments`、`summaries` 和 `processing_jobs` 表，并为会议时间、状态和全文查询建立索引。SQLite 已足以覆盖单用户本地场景，不需要首版引入服务器数据库。
8. **本地 UI/CLI**：至少提供开始、暂停、停止、选择输入设备、查看处理状态、查看历史、重试失败任务和导出 Markdown/JSON 的入口。现有命令行入口可以作为第一版控制面，但不宜继续把所有逻辑放在 `app_win.py`/`app_mac.py` 顶层。
9. **隐私和生命周期控制**：本地优先开关、远程 ASR/LLM 明确提示、录音/转写/纪要删除、保留期限、数据库备份和敏感信息日志脱敏。
10. **验证和可观测性**：无设备/权限/磁盘不足/模型服务不可用时给出可恢复错误；增加不依赖真实设备和服务的单元测试，再增加明确标记的硬件与服务集成测试。

## 平台限制、隐私和可靠性风险

### 平台限制

- Windows 的 `sounddevice` 基于 PortAudio，可枚举输入设备，但当前代码没有声明 WASAPI host API 或 loopback 参数。必须在目标机器上验证系统播放设备能否作为输入暴露；不同声卡驱动和 Windows 音频设置会改变结果。
- macOS 通常要求用户授权麦克风和系统录音，会议应用音频可能需要虚拟音频设备或专门的系统音频捕获 API。当前 `app_mac.py` 只能静态确认普通输入流路径，不能确认系统音频捕获可行。
- 两个入口在导入阶段就加载 Whisper/TTS 模型。启动慢、模型下载失败、CPU 内存不足或 GPU 不可用都会阻塞应用；会议应用需要把模型初始化和处理任务从录音线程隔离。
- Windows 中文 TTS 硬编码 `HKEY_LOCAL_MACHINE\\SOFTWARE\\Microsoft\\Speech\\Voices\\Tokens\\TTS_MS_ZH-CN_HUIHUI_11.0`，但这不影响纪要文本生成；若以后复用 TTS，必须改为设备发现和可配置 voice token。

### 隐私风险

- 会议音频和转写可能包含个人信息、商业秘密和第三方声音。默认设计应是本地 Whisper + 本地 Ollama/llama-server，并在调用远程 ASR/LLM 前显示明确提示。
- `transcribe_llama_asr()` 会通过 HTTP POST 上传音频；配置的服务地址可以是远程地址。不能因为 API 使用固定的 `sk-no-key-required` 就认为服务安全，必须支持鉴权、TLS、超时和访问控制。
- 原始音频、转写和纪要应分别可删除；日志不能打印完整会议内容；数据库和导出文件应按本机用户权限保护。
- “不让机器人加入会议”降低了会议平台集成和第三方 bot 权限风险，但不等于录音合规。用户仍需遵守所在地区和会议参与者对录音、通知和同意的要求；产品至少应提供明显录音状态和停止按钮。

### 可靠性风险

- 当前音频先累积在内存队列，进程崩溃、强制关闭或磁盘未落盘会导致整场会议丢失。
- 当前静音检测不是 VAD，系统通知、环境噪声和空闲输入可能导致误判；也没有回声消除、降噪、增益控制或说话人分离。仅用麦克风时远端声音可能无法可靠进入录音，取决于扬声器音量和房间声学。
- Whisper 整段处理长会议会带来内存、耗时和上下文问题；应采用可恢复分块和层级摘要，而不是把整场文本一次性塞给 LLM。
- 现有 ASR 网络错误有异常包装，但主流程没有持久化任务状态和自动重试；LLM、TTS、设备和文件写入也没有统一错误恢复机制。
- 项目没有自动化测试，且 README 与真实入口不完全一致。新增功能若继续集中在脚本顶层，后续维护和回归风险较高。

## 建议的最小可行架构

首版采用“本地桌面控制器 + 本地文件音频 + SQLite 元数据 + 可插拔 ASR/LLM 后端”，不引入机器人和云端服务。

1. **控制层**：新增会议服务而不是继续扩展 `app_win.py` 的顶层脚本。控制层创建会议、启动/停止录音、提交处理任务，并向 CLI 或后续 UI 提供状态。
2. **录音层**：抽取 `record_audio()` 的设备枚举和 PortAudio 基础能力；新增 `AudioCapture` 接口。Windows 首选普通麦克风和 WASAPI loopback 两种明确模式，音频块直接写到每场会议的目录，不把整场会议留在 `Queue` 内。第一版允许“选择一个设备”，不承诺麦克风与系统声道自动混音。
3. **存储层**：在用户数据目录创建 SQLite 数据库和会议音频目录。数据库保存会议元数据、音频文件路径、处理状态、转写段和纪要版本；原始音频与数据库分开，便于删除和重新处理。
4. **处理层**：停止录音后创建可恢复的处理任务：音频切块 -> ASR -> 保存带时间戳的转写 -> 分块摘要 -> 总结纪要。每一步写状态，失败后支持从最后成功步骤重试。
5. **AI 适配层**：复用 `transcribe_whisper()` 和 `transcribe_llama_asr()` 的后端思想，但统一为接口；复用 Ollama/OpenAI 兼容客户端思想，新增专用纪要 prompt 和结构化输出解析。首版默认本地 Whisper + 本地 Ollama/llama-server，远程后端必须由配置显式开启。
6. **呈现和导出层**：先提供 CLI：`start`、`stop`、`list`、`show`、`retry`、`export`。纪要显示原始转写来源和生成时间，导出 Markdown/JSON；后续再增加桌面或 Web UI。
7. **资源策略**：录音必须独立于 ASR/LLM 处理线程运行。会议数量不设产品上限，但显示磁盘占用，支持按会议删除原始音频、保留纪要或重新生成纪要。

## 分阶段实施计划

### 阶段 0：先验证平台和后端

- 在目标 Windows 机器枚举 PortAudio 设备，确认麦克风设备和 WASAPI loopback 设备是否出现，并分别录制短 WAV 做回放检查。
- 用现有 `stt-test.py` 或等价人工测试确认 Whisper 和 llama-server ASR 至少有一个可用；确认本地 LLM 能处理中文长文本。
- 测量 30 分钟音频的文件大小、Whisper 处理耗时和模型内存占用；这一步必须运行时验证，静态代码无法替代。
- 明确 MVP 先支持“麦克风”“系统 loopback”哪一种，还是要求用户使用系统混音/虚拟设备。若目标机器无法通过 PortAudio 获得 loopback，应暂停产品实现并先解决捕获方案。

### 阶段 1：可靠单会议录音和持久化

- 抽取可测试的音频设备、录音会话和 WAV 分块写入模块，支持开始/停止、设备选择、异常关闭和磁盘检查。
- 新增 SQLite schema 和会议状态，保证停止或进程重启后仍能找到已保存音频。
- 先实现 CLI 录音和会议列表，不接入 LLM；用模拟音频源测试写盘，用真实设备做集成冒烟测试。

### 阶段 2：离线转写

- 把 `stt.py` 的 Whisper/llama-ASR 适配为可替换接口，按固定时长切块并保存每块的状态、文本和时间范围。
- 增加重试、取消、断点续作和错误状态；原始音频必须保留到用户明确删除。
- 用短样本和一场真实会议验证中文/英文、长音频、设备噪声和模型资源占用。

### 阶段 3：自动纪要

- 为会议转写新增专用 LLM prompt 和结构化 schema，至少输出摘要、决策、行动项、负责人、截止时间、风险和待确认问题。
- 对长会议采用分块摘要再总结合并，并保留纪要版本和生成所用模型/提示版本。
- 加入 JSON 解析失败处理、长度限制和重试；允许用户重新生成纪要而不重新录音或转写。

### 阶段 4：日常可用性和隐私控制

- 增加历史搜索、Markdown/JSON 导出、删除/保留策略、磁盘占用提示、失败任务重试和明显录音状态。
- 增加本地/远程后端提示、配置校验、日志脱敏和数据库/音频备份说明。
- 再根据真实使用反馈增加实时转写、说话人分离、降噪、跨平台音频捕获和可选 TTS 朗读；这些不应阻塞第一版离线纪要。

## 最终建议

可以在这个仓库上做，但应把目标从“增强现有语音对话脚本”调整为“复用现有 AI 适配器、重新建立会议数据和处理架构”。最小成功标准不是 TTS 能回答问题，而是：用户能明确开始一场本地录音；录音过程中不因 ASR/LLM 处理阻塞而丢数据；停止后能恢复处理；重启程序仍能看到会议；最终能得到结构化纪要并保留可核对的带时间范围转写。

在实现前必须完成阶段 0 的设备和模型运行时验证。静态代码已经证明麦克风输入、Whisper、llama-ASR、Ollama/llama-server 和 TTS 的调用路径存在，但没有证明目标机器能捕获系统播放音频、模型服务可用、权限正确或长会议性能达标。
